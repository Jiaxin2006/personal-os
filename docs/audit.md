# 代码审查与验证结果

2026-11-05。审查对象为同级的 `sketchybar` 仓库，Git HEAD `14a63e0`；审查开始时工作树干净。另读取实际安装目录 `~/.config/sketchybar`，不把仓库版本假定为当前运行版本。

## 架构与数据流

```text
SketchyBar 事件（点击 / 定时刷新 / 休眠 / 唤醒）
  → plugins/timer.sh
  → plugins/timer.py main()
  → BEGIN IMMEDIATE → load → transition → 状态和历史一并提交
  → 更新菜单栏；保存后调用 focus.sh 更新当天轨迹

focus.sh → timer.py stats / durations
  → 本周 SQLite 已保存记录 + 旧版逐日日志 + 可选运行中记录
  → 当天 / 本周分类统计

clock.sh → 日期变化时重建当天轨迹
```

“自动计时”的现有含义是手动开始后持续累计，自动响应休眠和日期变化。没有发现按前台应用、窗口或文件自动识别工作类别的功能。`front_app.sh` 用于展示及操作其他应用的菜单，不参与时间归类。

`plugins/timer.py` 为 Python 标准库 + SQLite。`sketchybarrc` 和 Shell 插件负责呈现、交互和系统事件；其他插件覆盖 CPU、内存、网络、电池、音量、时钟、心情。可选 C helper 通过 Accessibility 和私有 SkyLight 接口操作菜单；当前前台菜单主要使用 AppleScript。

## 实际存储

现有仓库建表（`plugins/timer.py:64–75`）：

- `state(id, value)`：唯一状态行，JSON 包含 `mode/category/elapsed/anchor/last_tick/pending/notified`。
- `sessions(id, day, category, seconds)`：按自然日保存的秒数。一次跨日计时产生多行，没有统一 session ID。
- `discarded_sessions(id, discarded_at, state_json, restored_at)`：可恢复的丢弃计时。

现有账本可能包含旧引擎创建的额外表，例如 `recovery_events(evidence_key, session_row, details)`。备份和迁移时应完整保留。旧日志与 SQLite 记录的日期可能有交集，应先核对同一条记录在两个来源中的对应关系，再做汇总或迁移。

重要精度限制：`sessions` 只保留日期、类别和秒数；保存时 `write_session()` 按日期合并，丢弃原始起止时间。可以可靠计算每日时长和有效天数，但无法据此恢复“几点到几点”的历史时间轴，也无法恢复跨日记录之间的原会话关系。

## 具体发现

### P1：仓库安装会回退实际功能，并使阅读状态触发异常

位置：`plugins/timer.py:13,259`，`sketchybarrc:52,82`，`install.sh:20–23`。

安装版支持额外类别，例如 `reading`。仓库的 `render_timer()` 用 `CATEGORIES[state['category']]` 直接索引；用 `fresh('reading')` 调用已复现 `KeyError('reading')`，发生在调用 SketchyBar 之前。运行状态继续保留在数据库中，下一次刷新仍会遇到同样问题。

历史 `reading` 在仓库 `stats()` 里还会被合并为 `uncategorized`，造成分类展示回退。`install.sh` 虽然备份配置，但随后直接覆盖代码，不会合并这些本地改动。

处理顺序：先把安装版改动纳入审查过的基线，补 Reading / 未知类别 / 安装兼容回归；再做配置化。类别删除采用归档，禁止删除仍被记录或运行状态引用的类别。

### P2：仓库对外接显示器合盖模式误暂停

位置：仓库 `plugins/timer.py:317–320`。

仓库只检查 `AppleClamshellState = Yes`，外接显示器合盖办公时也会暂停。安装版新增 `lid_closed()`，同时要求 `AppleClamshellCausesSleep = Yes`，已修正这一判断。移植时必须保留，并用正常开盖、休眠合盖、外接屏合盖三种情形验证；真实设备行为仍需实测。

### P2：快速重启可能计入关机间隔

位置：`plugins/timer.py:311–315`；安装版同样存在。

仅当距 `last_tick` 超过 60 秒时才检查系统启动时间。若系统在最近一次 tick 后 60 秒内重启，当前逻辑不会检查 boot time，继续从旧 anchor 累计。

在临时数据库里，用 anchor=now−30、last_tick=now−20、假设 boot=now−10 的状态运行 mocked `main()`，启动时间查询没有执行，显示累计 30 秒；保守恢复到最近可信 tick 应仅保留此前 10 秒。该实验验证了代码分支，没有进行真实重启。

建议持久化 boot 标识，每次恢复核对；不同 boot 时在最后可信 tick 暂停。对同 boot 的计时进程意外退出也明确恢复策略，不将未知停机区间默认为工作时间。

### P2：现有备份方式不足以作为数据库迁移保障

位置：`install.sh:13–16`。

`cp -R` 会复制正在使用的 SQLite 数据文件，但不保证获得一致的数据库快照。未来执行历史迁移前，用 SQLite Backup API 获取可验证快照，并复制全部旧日志、配置、回收与恢复证据。文件复制本身不能替代迁移前后的逐类逐日核对和恢复演练。

### P2：分类切换语义会影响新产品的目标统计

位置：`plugins/timer.py:101–107,154–158`。

当前行为是“修正整次计时类别”，已有测试明确要求这样做。它不是按切换时刻切出一个新活动。如果先科研 1 小时，再切阅读 30 分钟后结束，整次 90 分钟都会归到 Reading。

保留旧类别选择器语义。新产品另加“切换活动”，在同一事务里结束旧活动、开始新活动；两个操作要有不同名称。不能悄悄修改旧语义，使既有操作和测试失效。

### 后续设计必须处理的限制

- `rows()` 只查询当前周；历史周、月趋势需要任意范围查询。
- 使用 `time.time()` 的墙钟差累计；校时、手动改时的跳变尚未覆盖。新核心需要单调时钟计算同一运行期时长、墙钟定位自然日，重启依靠已保存的可信状态恢复。
- 旧日志按文件日期归属，历史 SQLite 日期不随时区变化重新分配。不要给它们虚构 UTC 区间。
- 类别同时写在 Python 和 Shell 中，配置化时必须用同一来源生成菜单项与统计。
- 当前每秒运行脚本、查询 `ioreg` 并写状态，不等于一个持续运行的原生后台计时服务；将来需要实测能耗。
- SQLite 并发事件依赖调用方的 `BEGIN IMMEDIATE`；纯函数测试没有验证真实多进程竞争、双击及进程被杀。
- 旧日志重复导入、未知表保留、损坏状态 JSON、磁盘空间耗尽和未来版本数据库均缺少明确策略。
- `helpers/menus/menus.c:197–220` 使用私有系统接口；不能随新产品默认带入 App Store 构建。
