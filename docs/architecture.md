# 架构建议与数据模型

状态：供讨论的建议，不是已经选定或已经实现的架构。MVP 只做时间投入管理、周期任务与基础复盘；不实现账户、同步、交易或资产计算。

## 技术路线比较

| 方案 | 优势 | 代价与限制 | 适用阶段 |
| --- | --- | --- | --- |
| 保留 SketchyBar + Python + SQLite | 已有稳定交互、历史兼容、19 项回归；无需迁移计时语言 | 当前没有桌面主窗口；依赖外部工具；分发和沙盒适配工作多 | 现有用户使用及最初领域逻辑验证 |
| Tauri + React/TypeScript + SQLite | 适合复杂报表与 Web UI；可支持多平台 | 当前没有前端可复用；需引入 Rust/前端工具链；系统事件仍需平台代码；Python sidecar 的打包与签名需验证 | 如果未来明确需要 Windows/Linux 或团队主要使用 Web 技术 |
| SwiftUI + AppKit + SQLite | 与原生窗口、菜单栏、系统事件集成自然；适合当前仅 macOS 的定位 | 要学习/维护 Swift，并以对照测试迁移领域逻辑；现有 Python 不能直接视为 Swift 库 | 当前倾向的大众产品方向 |

建议：**先建立可验证的 Python 领域核心和旧数据适配，再决定主窗口技术；目标发布形态倾向 SwiftUI。** 先做一小段原生验证，确认菜单栏、睡眠事件、沙盒导入和关闭主窗口后继续计时，再决定是否开展原生迁移。不能为了“未来可能跨平台”立即把现有代码换成 Tauri。

Tauri 官方确有 [App Store 分发流程](https://v2.tauri.app/distribute/app-store/)，涵盖 sandbox entitlement、签名和 provisioning。它说明 Tauri 可采用该发布渠道，不说明当前插件、sidecar 和外部工具已经符合审核要求。

SwiftUI 提供 [MenuBarExtra](https://developer.apple.com/documentation/swiftui/menubarextra)；AppKit 的 [NSWorkspace 睡眠通知](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification)可作为原生系统适配入口。这是优先选择原生验证的技术依据，最终路线仍是本项目的工程判断。

## 分两阶段保护计时与数据

**兼容阶段：** 原计时器是旧时间账本唯一写入者。新领域模块读取原 SQLite 和日志，个人配置、目标、任务、复盘保存到单独的 `personal_os.sqlite3`。不要让 Dashboard 用旧 `connect()` 打开真实库，因为该函数包含建表操作；提供专门只读连接。

此阶段时间统计从来源账本读取一次，不先批量复制再叠加日志。新界面读到的运行中时间标记为“预览”，不当作已保存记录。仅预览刷新不修改历史。新窗口计时控制需走同一个命令处理器和事务锁，不能直接修改 JSON state；如果暂不能共享可靠入口，则先交付只读 Dashboard，不启动第二个计时器。

**原生接管阶段：** 对已停止写入的来源做一致备份，经 dry-run、校验后导入新的产品库。在短维护窗口结清或暂停当前活动，建立交接点，再启用新的唯一计时写入者。原 SketchyBar 计时插件随后只作为客户端或停用其计时入口，其他状态栏组件继续保留。新旧计时器不能各自累计同一段时间。

迁移必须携带來源 ID、原始类别、原始日期、精度和导入批次。旧数据作为 `daily_total` 展示，新数据才记录精确区间。原文件及未知表完整保留在备份中。

新产品库放在应用可写的 Application Support / 沙盒容器，用户用文件选择器导入和导出；不把 `~/.config/sketchybar` 作为公开产品的固定存储契约。

## 最小领域模型

产品用 Goal、Activity、Review 表达主要流程；周期任务需要独立的模板和实例，不能强行塞入目标进度。

| 对象 | 最小字段和规则 |
| --- | --- |
| Category | 稳定 ID、名称、颜色、排序、是否计入工作、归档标记；改名不改 ID |
| Goal / GoalVersion | ID、名称、类别或活动筛选、min/max/range/frequency/observe、阈值、强度、周起点、时区、生效日期；修改保留旧版本 |
| Activity | ID、唯一 category_id、日期/起止时间、有效秒数、来源、精度；旧记录允许只有日期和秒数 |
| ActivityGoal | activity_id + goal_id，关联多个目标；唯一约束防重复 |
| TimerState | 当前模式、活动 ID、可信累计、时间锚点、boot 标识、状态版本；同一时刻只有一个活跃活动 |
| TaskTemplate | ID、名称、描述、类别、周期规则、显示窗口规则、截止规则、开始日期、启停状态 |
| TaskOccurrence | ID、template_id、周期键、显示起止、截止日期、时区、规则与文案快照、状态、完成时间 |
| Review | ID、类型、周期、关联 occurrence_id、草稿/完成、结构化统计快照、用户正文、创建/更新时间 |
| ImportBatch / SourceRecord | 来源标识、内容校验、原行 ID/行号、导入结果与警告；保证重复导入不重复入账 |
| SchemaMigration | 数据库版本和迁移记录；遇到高于本程序支持的版本时停止写入 |

兼容阶段不要求先把全部旧时间转为 Activity 表；可以通过只读适配器提供相同的查询结果。原生切换时再物化导入。新库启用外键、事务、合理索引；不增加通用工作流、事件溯源平台或同步协议。

## 初始配置与统计口径

新用户的默认配置见 `personal-profile.example.json`（与 `personal_os/initial_profile.json` 相同），覆盖每种目标类型，用户可全部修改。

| 目标 | 规则 | 初始强度 |
| --- | --- | --- |
| 总工作 | ≥20h/周，仅累加计入工作的活动一次 | 硬性 |
| 科研时长 | ≥10h/周 | 硬性 |
| 科研频率 | ≥4天/周，各有效日科研累计≥1.5h | 硬性 |
| 课程学习 | 4–6h/周 | 弹性 |
| 行政与杂务 | ≤5h/周 | 弹性 |
| 其他工作 | 仅记录 | 观察 |
| 阅读 | ≥3天/周，各有效日阅读累计≥30min | 弹性 |

默认周一开始，时区取本机设置，均可编辑。历史记录沿用已经存下的日期；新精确区间按明确报告时区拆分。更换报告时区只对新规则生效，不悄悄改写旧日级记录。

有效天数：对选中周的每个本地日期，将符合目标的活动秒数求和，再统计 `day_seconds >= min_daily_seconds` 的不同日期数。不先四舍五入成分钟再判断。

- 科研一周 10h，但仅 3 天各≥1.5h：时长达标，频率 3/4 未达标，分别显示。
- 阅读一天 90min：1/3；三天各 30min：3/3；每天两段 15min 可累计为当日 30min；29min59s 不达标。
- 运行中预览可显示“按当前计时预计达标”，正式周复盘以已保存数据生成，并固定所用目标版本。
- 最大值目标在未超过时显示“当前未超限”；周尚未结束时避免显示最终通过。范围目标区分低于/范围内/高于；观察目标不标失败。
- 周中编辑默认下一周生效，明确选“本周生效”时展示影响；已完成复盘不随改目标自动改变。

类别规则：一段时间只有一个类别，可关联多个目标；总工作不通过累加目标进度计算，避免双算。旧记录中没有类别的部分归 `uncategorized`（未分类），默认不算入工作。阅读默认不计入总工作，用户可以修改。

## 周期任务的精确定义

MVP 支持固定的周、月、季度、年规则和简单编辑表单，不先实现任意自然语言或全部 RFC 5545。模板编辑影响未来尚未生成的实例；已经完成或打开的实例保留规则快照。归档模板不删历史。

每个实例以 `(template_id, period_key)` 唯一，生成/补生成使用幂等事务。应用关闭数月后，下次启动仍能为启用后的遗漏周期补齐实例；不只保留最新一期。历史列表分页，Dashboard 将过期未完成任务折叠为明确的逾期入口，避免一次淹没日常视图。

月末最后 7 天的计算使用自然日期：

```text
last_day = 本月最后一天
visible_from = last_day - 6 个自然日
due_on = last_day
due_exclusive = 下月 1 日 00:00（实例时区）
```

2026 年 11 月为 11/24–11/30，11/23 不显示；2 月为 2/22–2/28，闰年 2 月为 2/23–2/29。不要用固定 7×24 小时推算自然日。`visible_from` 和 `due_on` 是两个独立字段，不依赖待办是否提前创建。

日常待办只展示已进入显示窗口的待办及单列的逾期项。未来实例仍可在完整任务列表查看。完成、跳过和逾期未完成要可区分；到期不自动完成，进入下一期不重置上一期。晚完成写回上一期实例，不能误勾当期。复盘正文绑定实例 ID，不能只绑定模板 ID。

初始模板：周日时间复盘、月末最后 7 天月度复盘、季度末最后 7 天季度复盘。月度复盘是手工文字模板。

## 数据保护、导出与发布验证

历史迁移前必须有 SQLite Backup API 快照、旧日志与配置副本、校验清单和恢复路径。迁移先在副本 dry-run，再逐来源、逐日、逐类别比对秒数；`daily_total` 记录保持精度标识。日志导入成功后由导入清单决定是否已计入，不能继续重复读取叠加。文件内容变化时提示冲突，禁止无声二次入账。

导出提供用于恢复的带版本 JSON/备份包，以及便于分析的 CSV。备份包含配置、目标版本、任务模板与所有实例、复盘、来源证据、计时状态和丢弃恢复信息；CSV 不作为唯一备份。恢复先校验到新位置，成功后切换，不覆盖现有文件赌恢复结果。

Mac App Store 发布需要开启 [App Sandbox](https://developer.apple.com/documentation/security/app-sandbox)，并使用[用户选择文件及持久访问机制](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)处理导入导出。登录与后台组件可研究 [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)。这些能力仍需用实际签名和沙盒构建验证，不能据此承诺一定通过审核。

发布验证单独安排：关闭窗口与退出应用的不同计时行为、睡眠/唤醒/重启、外接显示器合盖、沙盒文件授权的重启保留、签名与安装升级、启动项、能耗。现有 CPU/菜单模拟/私有 C helper 不属于 Personal OS 必需功能，继续留在旧配置，不带入新 App Store 产品构建。
